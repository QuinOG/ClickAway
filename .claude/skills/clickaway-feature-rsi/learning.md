# Feature RSI learning

## Active lessons

1. (Provisional, 1 supporting run) On Windows, write non-ASCII UI text with the Edit/Write tools, not a PowerShell pipe or here-string, then grep the changed files for stray `?` or U+FFFD. Scope: any trial that adds copy containing `·`, `—`, or similar characters. Test: the next trial that adds such copy finds no garbled characters in review.

2. (Provisional, 1 supporting run) For any change that moves or adds visible UI, measure element positions in a real browser at 1440 and 390 wide before review (bounding boxes, not screenshot reading). Scope: layout-affecting trials. Test: in trial 002 this caught a note covering the chart's bars on phone before the reviewer saw it.

3. (Strong: direct user feedback, 2026-11-13) Reviewers judged whether each change worked, never whether it was wanted or better than before. That let trials 1-2 make History worse and trial 6 add something the user didn't want. Get the user's OK before adding a feature they didn't ask for, and judge each change against what was there before, not only against its own pass conditions. (Since 2026-11-15 the user has handed direction to Claude, so new features no longer need a separate OK during the hand-off; the "better than before" test still applies.)

4. (Provisional, 1 supporting run) Before trusting any browser capture or Playwright result, check which process serves port 4173. Playwright reuses an existing server, and agents leave dev servers running in their worktrees. Run 2 got unchanged "after" shots and a false all-pass from another worktree's server. Scope: every capture and browser suite run. Test: the next run checks the port owner first and runs captures from its own server on another port (`SHOT_BASE_URL`).

5. (Provisional, 1 supporting run) When a change adds or reveals text in a shared component, measure the primary action at 390 wide in every state that uses the component, not just the one being changed. In 009, revealing coach text for new players pushed Start off the screen for two other onboarding states. Scope: shared lobby, Results and dialog components. Test: the next trial touching a shared component lists the states it measured.

6. (Provisional, 1 supporting run) An automated layout audit only finds what it looks at: the device audit passed a live round whose timer was covered on phones and a top bar whose Help and Settings sat under the player card, because it skipped anything inside a fixed layer and anything not on top. Read the screenshots of the core screens (live round, lobby, Results, nav) by eye at phone, sideways phone and tablet sizes, and when the eye finds something the audit missed, extend the audit and confirm it flags the old code. Scope: any device or layout pass. Test: the next pass records which screenshots were read by eye and any audit rule added.

7. (Provisional, 1 supporting run) Measure a shared screen in every state a player can put it in, not only its default: on the lobby that means each mode selected. Trial 014's layout checks used Casual only; Ranked's status panel had been squeezed into the stage column and Practice's drill lab shrunk to 2px on phones and tablets since an earlier CSS change, and neither audit nor trial saw it until a reviewer's CSS reading prompted measuring all three modes. Scope: lobby, Results and any screen with tabs or modes. Test: the next layout trial's record lists the states measured; `tests/e2e/lobby-modes-fit.spec.js` now guards the lobby.
